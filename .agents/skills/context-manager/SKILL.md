# Context Manager Skill

此 Skill 通过**三层防线**控制上下文消耗，同时确保跨对话不丢失关键信息。

```
防线1：防膨胀（少读、少写、精准操作）
防线2：主动分裂（检测到过重时建议开新对话）
防线3：检查点接力（新对话瞬间恢复状态）
```

---

## 防线1：上下文防膨胀规则（对话内）

**这是真正控制上下文大小的核心。** 以下规则在每次对话中必须始终遵守：

### 📖 文件读取节约

1. **按需读取**：不要"为了全面了解"而读取整个文件。先问自己：这次操作需要看哪几行？
2. **用行号范围读取**：优先使用 `view_file` 的 `StartLine`/`EndLine` 参数，只读必要片段
3. **不重复读取**：同一个文件在一次对话中尽量只读一次，利用已有记忆
4. **grep 优先于全文读取**：定位问题时先用 `grep_search` 缩小范围，再用 `view_file` 读目标行

### ✏️ 回复节约

1. **不回显大段代码**：改完文件后不要在回复中再贴一遍代码，简述改了什么即可
2. **不复述文件内容**：读取文件后直接执行操作，不要向用户总结文件内容
3. **表格优于长文**：汇报多项改动时用表格，不用逐条长段描述

### 🔧 工具调用节约

1. **合并并行调用**：能同时调用的工具一次性发出，不要分轮
2. **避免探索性调用**：不要"先 list_dir 看看有什么"，尽可能利用检查点中的文件速查
3. **一次到位**：编辑文件时尽量一次 `multi_replace_file_content` 改完，避免对同一文件多次操作

## 防线2：上下文健康监测与主动分裂

### 自我监测指标

在对话过程中，持续关注以下信号：

| 信号 | 说明 | 动作 |
|---|---|---|
| 对话超过 **8 轮** 且涉及多文件编辑 | 上下文已较重 | ⚠️ 提醒用户可考虑开新对话 |
| 单次对话读取了 **5 个以上不同文件** | 上下文膨胀明显 | ⚠️ 完成当前任务后建议分裂 |
| 用户提出了 **第二个不相关的任务** | 话题分叉加重上下文 | 🔴 建议开新对话处理新任务 |
| 出现 **工具调用超时/失败** | 可能是容量预警 | 🔴 立即保存检查点，建议开新对话 |

### 分裂流程

当触发分裂建议时，按以下顺序执行：

```
1. 完成当前手头的操作（不要做到一半就断）
2. 更新 CONTEXT_CHECKPOINT.md（覆盖写入）
3. 更新 DEVELOPMENT_LOG.md（追加日志）
4. 向用户建议：「当前对话上下文较重，建议开新对话继续。我已保存检查点，新对话会无缝衔接。」
```

## 防线3：检查点接力机制（跨对话）

### 检查点文件

文件路径：`{项目根目录}/CONTEXT_CHECKPOINT.md`

```markdown
# 上下文检查点

> 最后更新：YYYY-MM-DD HH:MM

## 🎯 当前焦点
[一句话描述当前状态]

## 📁 近期修改文件
| 文件 | 修改摘要 |
|---|---|
| `path/to/file.py` | 简述改动 |

## ⚠️ 待办 / 未完成
- [ ] 待完成事项

## 🧠 关键决策与上下文
- [技术决策、用户偏好、容易遗忘的背景]

## 🔗 相关文件速查
- 入口：`main.py`
- [核心文件路径列表]
```

### 写入规则

1. **50 行以内**，只保留对下一次对话有价值的信息
2. **全量覆盖**，不追加历史（历史由 `DEVELOPMENT_LOG.md` 负责）
3. **只记结论**，不记录过程讨论

### 触发写入

1. **完成功能开发或 Bug 修复后**
2. **用户明确要结束对话或开新对话时**
3. **触发防线2的分裂建议时**

### 触发读取

1. **新对话首次涉及项目代码操作前** — 先读检查点，默默消化不复述
2. **用户提到"继续"、"接着做"、"上次"等接力词语时**
3. 如果检查点超过 7 天，提醒用户确认是否仍有效

## 与其他 Skill 的协作

| Skill | 职责 | 触发 |
|---|---|---|
| **context-manager** | 记录"现在"，控制上下文 | 每次对话自动 |
| **project-logger** | 记录"过去"，不可变历史 | 任务完成时 |
